### 当前结论与证据

| 结论 | 证据 |
| --- | --- |
| 任务是核心，日期和阶段是独立维度 | types.ts、db.rs 中的 due_date、status、stage、两套排序字段 |
| 多视图来自同一任务集的分组与布局 | grouping.ts、board.ts、CalendarView.tsx |
| 快速输入是规则加日期解析 | nlp.ts 中优先级 / 重复正则、已有标签匹配、chrono.parse |
| 语音是本地引擎转写，添加仍需确认 | voice.rs 与 voice/audio.rs；录音转 WAV、运行引擎并读取 JSON |
| 托盘提醒由后台轮询驱动 | scheduler.rs 的 20 秒循环 |
| 计时器有 12 小时安全上限 | timer.rs 的 MAX_SESSION_SECS，与 README 的笼统描述有差异 |
| 重复任务是原地更新下一期日期 | commands.rs 的 toggle_task 及 recur.rs，没有该路径的独立完成历史行 |
| 日志摘要是计数文本 | journal.ts 的 daySummary / summaryText |
| 账号同步采用时间戳覆盖与删除标记 | sync.ts / sync.rs；轮询退避与编辑防抖 |
| 日历为单向任务推送 | googleCalendar.ts 的专用日历 scope 与本地链接；events 不在同步内容中 |
| 应以源码可见项目记录其许可 | LICENSE 自定义条款，对分发、托管与付费资格有限制 |

## 2026-10-21 · 补充我们的理解与一图总结

- 根据对话补充三层理解：任务数据是管理对象，列表 / 看板 / 日历是管理界面，新增修改、状态流转、提醒、计时、保存与同步是驱动逻辑。
- 将本质明确为以任务为中心的个人管理软件；日历是按时间查看任务的视图，实际工作内容和规划仍由使用者决定。
- 增加一张完整总结图，涵盖我们的理解、库的能力、本质、效果与参考价值。产品画面使用上游 Board 原图，图中文字与布局为我们的分析，没有重新模拟产品界面。
- 对我们的意义具体写成：优先参考看板分列、数量、卡片间距与视觉层级，以及优先级 / 标签 / 日期 / 进度等信息组织；理解拖动交互与业务状态的关系，再结合自己的流程实现。
- 原始 PNG / SVG 位于 assets/，网页副本位于 web/assets/；生成脚本为 scripts/build_summary.py，记录依赖、中文字体、源图哈希与输出哈希。
- 已直接检查生成的 PNG 排版与可读性；脚本核对文本宽度和画布边界，网页部分沿用静态资源与原图来源校验。
