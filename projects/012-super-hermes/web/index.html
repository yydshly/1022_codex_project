READ THIS FIRST / 我们的理解摘要

先用五个问题，讲清它的能力和价值。

能力是什么？
辅助 AI 定位问题、审查代码与方案。输入现象和相关材料，指导 AI 设计查法、找可疑位置与触发条件、检查反例、说明结论依据和遗漏。可用于内存增长、并发异常、失败恢复、性能退化与设计权衡；原库代码分析重点是单文件。
底层原理是什么？
Markdown 提示词＋上下文工作流。Skill 写明检查动作、顺序、角度与产物，模型结合具体材料选择方法并分析；宿主提供读写、执行与测量工具。历史盲区进入后续上下文。约束主要是自然语言指令，效果取决于模型、材料、工具与验证。
包含哪些模块？
5 个 Skill：scan 定向检查；full 多轮分析与反驳；3way 从结构、时间和目标冲突审查；discover 列调查方向；reflect 复查并记录盲区。
7 份视角模板：错误韧性、结构权衡、性能成本、接口与行为、信息损失、假设反转、长期演化。历史记录：.prism-history.md 保存侧重、遗漏和建议。查看模块与原文 →
具体步骤是什么？
我们的七步：定义问题 → 建立事实基础 → 提出候选解释 → 设计并执行检查 → 收敛并反驳根因 → 验证修复 → 报告与沉淀。③–⑤循环，修复步骤按任务适用；最终交付九项结论报告。七步与完整报告是我们基于上游提炼的通用协议，原库各 Skill 按职责选用。查看每步输入、要求与产物 →
对我有什么意义？
把排查经验沉淀成可复用、可核查的 AI 工作规范。在不同项目保留输入、假设、检查、反驳、报告与验证要求，替换领域清单和工具；让 AI 的交付更便于检查和交接。先将其用作团队定位协议，再按需要增加证据校验和阶段门禁；复用价值需在自己的任务中验证。

判断与具体查法由模型完成；Skill 组织可见动作，证据检验结论。网页保存研究材料与教学案例，没有在线模型接口；内存和并发复现支持具体缺陷机制，不代表已评测 Skill 的检出效果。

OUR UNDERSTANDING / 从规则到通用定位协议

Skill 定步骤，模型找原因，证据决定结论。

下载七步协议与报告 TXT ↓

我们的核心理解：这个库的价值，是把问题定位与审查的经验，整理成多个可复用 Skill。它没有替模型完成推理，而是约定“先检查什么、从哪些角度查、每步留下什么、怎样复查”。具体查法与判断仍由模型完成，正确性要靠材料和执行证据检验。

模型 / 分析与判断

结合当前问题选具体查法

解释代码和数据、提出假设、选择检查、综合证据。能力与遵循程度会影响效果。

Skill / 可见动作与产物

规定怎样调查和交付

用自然语言规定顺序、检查角度、反驳要求、报告字段和盲区记录；不能锁定模型内部思维。

宿主与证据 / 执行和检验

提供工具，核对判断

宿主提供权限和工具；日志、复现、测量与回归结果用于检验候选原因和修复效果。

原库能力与我们的提炼要分清：上游提供 5 个入口及其各自流程；下面七步、完整报告和修复验收，是我们基于它整理的通用协议。它们不是原库内置的七阶段执行器，也不要求把所有 Skill 顺序运行一遍。原库代码分析侧重单文件，跨项目使用需补充上下文和工具适配。

输入约定

先把现象和材料交代清楚。

最小输入：问题现象（预期与实际、触发条件）＋项目或材料入口。

按需补充：环境、最近变更、日志、最小复现、允许操作范围、是否需要修复、完成标准。缺少的材料先记为缺口。

七步：从现象到可以核查的结果

顺序与输入怎样指导 AI本步产物与约束
01定义问题现象、预期、材料入口写明预期与实际、触发条件、影响范围、完成标准，确认任务是否包含修复。问题定义＋范围＋验收条件
尚不明确的条件列为待确认。
02建立事实基础问题定义与相关材料读取代码、配置和运行证据，建立最小复现，追踪现象沿哪些路径传播。事实＋复现＋路径＋缺口
标明来源；代码推演与实际运行分开。
03提出候选解释事实、可疑路径与缺口提出合理假设，逐项写出支持依据、可检验预测和推翻条件。可区分、可反驳的候选
候选不能直接当成已证实根因。
04设计并执行检查候选及其预测优先选择低成本、能区分候选的检查；每次改变一个主要条件，比较预期与实际。目的＋方法＋预期＋实际
如实报告执行；未运行标为推演或待验证。
05收敛并反驳根因检查结果与候选按证据更新、排除候选，建立因果链；主动寻找反例、替代解释和成立边界。根因或剩余候选＋排除依据＋成立条件
证据不足返回第 3–4 步，不强行结案。
06验证修复定位结果、范围与验收条件任务包含修复时，针对原因做修改，在原触发场景比较前后结果，再检查相关回归。修改＋前后对照＋回归结果
只定位时可不修改；未验证不得声称已修复。
07报告与沉淀调查记录与修复状态按下方九项报告交付；保存可复用查法、适用条件、盲区和下次补查方向。结论报告＋下一步＋可复用经验
完整故障档案需要另行存储。

循环关系：③ 候选 → ④ 检查 → ⑤ 收敛 / 反驳 → 返回③或④。七步规定调查主线，具体检查内容随问题、证据和项目变化。

DELIVERABLE / 以这份结论报告为准

最终交付：九项报告，允许证据不足。

先明确结论状态，再说明依据；不能把“走完流程”当成“已经定位”。

根因已有证据支持候选待验证尚未定位
01 · 结论状态
从三种状态中选择，并说明证据强度。
02 · 问题与影响
预期、实际、影响范围。
03 · 定位位置
文件、函数、配置、依赖或环境。
04 · 触发条件
什么时候发生，什么时候不发生。
05 · 因果链
条件 → 异常状态或动作 → 最终结果。
06 · 证据
来源、方法、实际结果；区分事实与推演。
07 · 其他解释
已排除、未排除的解释及其依据。
08 · 修复与验证
修改内容、原场景对照、相关回归。
09 · 局限与下一步
缺失证据、未覆盖范围、下一项检查。

不适用或未执行的字段须如实说明。根因应解释触发条件与传播过程；修复结论需要原场景和相关回归证据。

对我们的价值

把个人排查经验变成团队可复用的输入、动作、产物与验收约定。内存、并发、接口错误、性能退化或配置故障共用主线，按项目替换领域清单、材料入口和检查工具。

约束能做到什么

原库主要用提示词引导，不能保证每步都执行或判断都正确。需要更强约束时，另加阶段产物校验、工具证据要求、权限控制和失败回退；这些工程扩展未在原库完整实现。

      01 / 流程
      先做什么，后做什么。
      先公开方法
      scan 先生成并展示 75–200 单词的专用检查方法，然后执行。
      逐轮传递结果
      full 设计 2–4 轮，后轮接收原材料和前轮分析。
      加一道反驳环节
      full 必须另做对抗复查；discover 只列方向，不提前下结论。
      作用：让分析有顺序、有中间产物，也允许推翻前面的判断。
      流程依据 ↗
      
            
      02 / 规范
      什么才算交付完成。
      问题要可定位
      发现表包含位置、什么会出错、严重程度、可修复或结构性问题。
      错误要明确撤回
      指出什么证据会推翻结论，纠正过度断言并补上遗漏。
      范围要交代清楚
      列出侧重点、未查角度和下一步建议，reflect 将记录追加到历史。
      作用：把“说得很深入”变成可以逐条核查的报告要求。
      报告依据 ↗
      
            
      03 / 角度
      从哪里看，做什么检查。
      先选领域
      discover 列约 10–20 个不同方向；scan 再结合用户重点与历史遗漏定制。
      固定三种视角
      WHERE 查结构依赖，WHEN 推演变化，WHY 检查目标之间的冲突。
      把角度写成动作
      追踪错误传播、反转假设、比较接口承诺与行为，或构造线程交错。
      作用：明确观察对象、检查动作和产出，给多角度分析具体抓手。
      视角依据 ↗
      
          
      
          
      约束通过提示词实现
      阶段标题、角色、数量、输出字段和“必须执行”等指令负责引导模型；仓库没有逐阶段程序校验来保证遵守。复用时保留反例、复查和盲区说明，同时允许“证据不足”或“未发现必然冲突”，避免预设一定存在守恒律。

      通用问题定位协议 · 本研究提炼版
日期：2026-10-22
参考：Cranot/super-hermes @ ffe2d10042041dcc23325f013e8b7e607e069952

【定位与边界】
Super Hermes 提供 5 个 Markdown 分析 Skill 和 7 份固定分析模板。
作者把通用检查动作、顺序、角度、报告要求和盲区记录写成自然语言指令。
模型根据材料选择具体查法、解释证据并作出判断；工具执行和权限由宿主提供。
Skill 约束可见动作和交付产物，不能读取或锁定模型的内部思维。
仅有提示词约定不能保证遵循，也不能保证结论正确。事实与运行结果用于检验判断。
以下七步、完整报告和修复验收是我们的通用协议，不是上游内置的七阶段执行器。
上游代码审查以单文件为主；跨项目使用需要补充项目上下文、工具与证据适配。

【输入】
最小输入：问题现象（预期与实际、触发条件）＋项目或材料入口。
按需补充：环境、最近变更、日志、最小复现、允许操作范围、是否需要修复、完成标准。
材料不足时先记录缺口；不得编造日志、运行结果或已有结论。

【七步流程】
1. 定义问题
输入：现象、预期、材料入口。
要求：说明预期与实际、触发条件、影响范围和完成标准；区分定位与修复任务。
产物：问题定义、调查范围、验收条件；不明确的条件列为待确认。

2. 建立事实基础
输入：问题定义与相关材料。
要求：读取相关代码、配置和运行证据；建立最小复现，追踪现象的传播路径。
产物：有来源的事实、复现步骤、相关路径与证据缺口。
要求：代码推演与实际运行分开记录；无法复现可以继续，但必须标明。

3. 提出候选解释
输入：已知事实、可疑路径与缺口。
要求：提出合理的候选解释；逐项写出支持依据、可检验预测和推翻条件。
产物：可被区分、可被反驳的假设列表；不得把候选直接写成已证实根因。

4. 设计并执行检查
输入：候选解释及其预测。
要求：优先选择低成本、能区分候选的检查；每次改变一个主要条件。
产物：检查目的、方法、预期、实际结果与执行状态。
要求：只能如实报告执行；未运行必须标为推演或待验证。

5. 收敛并反驳根因
输入：检查结果与候选解释。
要求：按证据更新或排除候选，形成条件→异常状态或动作→结果的因果链。
要求：主动检查替代解释、反例与适用边界；证据不足时返回第 3–4 步。
产物：有证据支持的根因，或仍待验证的候选；附排除依据与成立条件。
第 3–5 步可以循环，不得为了走完流程强行得出唯一根因。

6. 验证修复（仅任务包含修复时）
输入：定位结果、修复范围与验收条件。
要求：针对原因做修改；在原触发场景下比较前后结果，并检查相关回归。
产物：修改内容、前后对照、回归结果与未覆盖范围。
要求：只定位时可不修改；没有完成验证不得声明“已修复”。

7. 报告与沉淀
输入：调查记录、证据、候选与修复状态。
要求：按下列九项报告交付；保存可复用查法、适用条件、盲区和后续检查方向。
产物：结论报告＋下一步＋可复用经验；完整故障档案需要另行存储。

【结论报告：九项字段】
1. 结论状态：根因已有证据支持 / 候选待验证 / 尚未定位。
2. 问题与影响：预期、实际、影响范围。
3. 定位位置：文件、函数、配置、依赖或环境。
4. 触发条件：什么时候发生，什么时候不发生。
5. 因果链：条件 → 异常状态或动作 → 最终结果。
6. 证据：来源、检查方法、实际结果；区分事实、推演和待验证内容。
7. 其他解释：已排除与尚未排除的解释及其依据。
8. 修复与验证：是否修复、修改内容、原场景前后对照、相关回归。
9. 局限与下一步：缺失证据、未覆盖范围、下一个最有效的检查。
不适用或未执行的字段须如实说明；不得用空白冒充完成。

【验证要求】
- 事实、假设、代码推演和实际执行分别标记，并保留来源与复现方式。
- 根因应能解释触发条件和传播过程，还需检查有竞争力的替代解释。
- 没有实际运行，就不能声称运行验证通过。
- 任务包含修复时，原场景验证和相关回归都应留下结果；缺项列为未完成。
- 证据不足时允许交付候选待验证或尚未定位，并指出下一步。

【从上游复用什么】
scan：先生成针对材料的检查方法，再执行，交代问题位置与盲区。
full：自行规划 2–4 轮，并额外对抗复查，修正或撤回发现。
3way：结构（WHERE）、长期变化（WHEN）、目标冲突（WHY）三个视角。
discover：只提出约 10–20 个调查方向，不代替深入分析。
reflect：复查侧重与遗漏，追加 .prism-history.md，供后续补查。
七份模板：错误韧性、结构权衡、性能成本、接口与实际行为、信息损失、假设反转、长期演化。
本协议按问题按需选用这些能力，不要求把 5 个 Skill 或 7 份模板全部运行一遍。

【对我们的价值】
把排查经验变成可复用的输入、动作、产物与验收约定，减少漏查与无法复核的结论。
不同项目保留通用流程，替换领域检查清单、材料入口和工具适配。
需要更强执行约束时，另行实现阶段产物校验、工具证据要求、权限控制和失败回退。
这些工程扩展在原库中没有完整实现；本研究未运行 Hermes 或评测模型增益。

      刚失败，为什么又允许请求了？
