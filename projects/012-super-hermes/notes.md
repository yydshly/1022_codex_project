## 2026-10-22 · 用内存增长解释具体能力

用户指出页面缺少“内存泄漏定位”的体现。核对固定版本后，发现 optimize 模板确实覆盖分配与缓存成本，但现有快照没有专门的内存泄漏检测实现和经过运行验证的内存泄漏案例。不能把一般代码审查能力写成已经验证过的诊断效果。

因此补充了明确标注来源的自建机制案例：`UnboundedCache` 每个新 key 保留 64 KiB；`BoundedCache` 使用最多 32 条的 LRU 淘汰。`reproduce_memory.py` 在独立子进程分别处理 800 个不同 key，0/200/400/600/800 请求时执行 GC 并记录 tracemalloc 数据，比较快照找到第 11 行分配，再清空缓存确认该响应分配增量归零。

本轮测得无上限版本约 50.126 MiB、800 条；有限版本约 2.010 MiB、32 条。数据为 Python 跟踪存活分配相对空缓存的增量，不是进程 RSS；没有模拟服务吞吐、真实堆转储或原生内存泄漏。固定样例哈希、环境、时间、分配行和全部采样保存在 `web/assets/memory-reproduction.json`，同份数据嵌入 `web/memory-data.js` 供直接文件模式使用。

网页把“现象 → 生命周期检查 → 分配与持有位置 → 修改与运行检验”放到总览图之前，新增内存场景、曲线采样器、代码与 JSON 下载。说明、代码和修改由本研究编写，本轮未运行 Hermes 或模型，不能把结果算作 Skill 检出率或增益评测。上游快照不改动。
