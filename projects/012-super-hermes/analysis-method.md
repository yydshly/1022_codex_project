# Super Hermes 如何约束 AI：流程、规范与角度

这是从固定上游版本 `ffe2d10042041dcc23325f013e8b7e607e069952` 的五个 Skill 提炼的分析方法。下文区分上游实际指令与我们的复用建议；“要求”表示提示词指令，不能等同于程序强制。

完整规则现已覆盖五个 Skill 和七份固定模板，按动作归纳 69 条（12 通用、27 入口专属、26 固定视角、4 实现边界）。[中文全表](web/assets/super-hermes-rules.txt) 与 [结构化全表](web/assets/super-hermes-rules.json) 为网页同源导出；每条给出动作、引导作用、产物、教学例子、边界与固定版本原文行号。原文要求与研究者解读分字段保存。

固定模板的细项包含错误边界与多跳损害、两种相反修复、L12 反复改进与元层次检查、性能数据与量化、接口承诺错位、异步状态交接、搜索优先级、空值组合、经验假设反转、五类维护周期及模拟自查。元数据、评分、模型推荐、工具声明和无工具运行选项在边界组单列，不混作已执行的约束。

## 先沿一个问题走：从内存增长到定位结论

它把问题定位经验沉淀成三层可复用材料：作者写入 Markdown 的分析规则、根据当前问题生成的具体方法、由 reflect 记录并供下次 scan 读取的分析盲区。scan 默认每次重新设计方法，七份固定模板是按需选择的替代材料。仓库没有显示一套自动从故障案例中训练方法的系统。

现行教学统一采用讨论形成的七步协议。下面是研究者编排的内存案例，不是一次 Hermes 运行记录；输入、假设列表、完整报告与修复验收是我们的提炼与扩展。

| 阶段 | 给 AI 的具体要求 | 本例留下什么 |
| --- | --- | --- |
| 1. 定义问题 | 区分预期与实际，说明范围、触发条件与完成标准 | 请求增多时存活内存上涨；先查自建缓存，要求解释并验证 |
| 2. 建立事实基础 | 设计贴合当前材料的查法，读取代码和运行证据，记录缺口 | 第 11 行分配 64 KiB 响应，第 20 行缓存持有；需验证退出路径 |
| 3. 提出候选解释 | 为候选记录依据、预测、反证条件 | 无界缓存保留；或另有引用；比较不同 key、重复 key 与清空后结果 |
| 4. 设计并执行检查 | 选择低成本区分检查，如实记录方法、预期与实际 | 不同 key 无界约 50.126 MiB；同 key 约 0.065 MiB；32 条 LRU 约 2.010 MiB |
| 5. 收敛并反驳根因 | 比较证据、检查替代解释，建立因果链，不符则返回 3–4 步 | 长期缓存无淘汰 → 新 key 响应一直可达 → 存活内存增长；清空后释放 |
| 6. 验证修复 | 仅修复任务适用；原场景对照与相关回归，说明未覆盖范围 | LRU 对照保持 32 条；代价是重新生成；真实业务与并发回归未覆盖 |
| 7. 报告与沉淀 | 按九项报告交付，保存查法、适用条件、盲区和建议 | 结论状态、问题与影响、定位位置、触发条件、因果链、证据、其他解释、修复与验证、局限与下一步 |

第 3–5 步循环；只定位时可以不修改。结论允许为“根因已有证据支持 / 候选待验证 / 尚未定位”。事实、假设、代码推演与真实执行分开，未运行不得报告验证通过。

第 4 步数据已由 `scripts/reproduce_memory.py` 在独立子进程实测，每组 800 次请求、每条响应 64 KiB，采样前执行 GC；清空缓存后各组响应分配行的增量均归零。度量为 Python 跟踪存活内存增量，非 RSS。见 [memory-reproduction.json](web/assets/memory-reproduction.json)。方法、定位、修复对照由研究者编写，没有执行模型检出测试。

**“沉淀”的准确范围：**Skill 保存通用动作和交付规则；Generated Lens 是本次生成的检查方法，scan 不保证自动存档；`.prism-history.md` 主要保存分析侧重、遗漏和后续建议，默认没有完整故障报告、修复补丁与测试证据。把它扩展成团队故障知识库需要另加归档结构与验证流程。

## 1. 流程：约束先后顺序、轮次和中间产物

| 上游做法 | 具体约束 | 可以借鉴什么 |
| --- | --- | --- |
| scan 先设计，再执行 | 先读材料与可选历史，再生成并展示 75–200 单词的专用分析方法，然后执行 | 先把“准备怎么查”变成可见产物，便于检查方法是否贴合问题 |
| full 逐轮传递结果 | 设计 2–4 个轮次；后续轮次接收原材料和全部前轮输出 | 用前轮结果深化检查，明确每一轮的输入 |
| full 必须反驳 | 另加一次未预先设计的对抗轮次，寻找反证、过度断言和遗漏，撤回错误判断 | 给结论设置复查环节，允许推翻自己 |
| reflect 分析自己的输出 | 先分析对象，再把第一轮输出当作新材料分析，最后报告并保存盲区 | 把“报告是否可靠”和“原对象有什么问题”分开检查 |
| discover 限制本轮职责 | 只列研究方向，不生成分析提示词，也不做实质分析 | 给阶段设边界，避免方向探索和结论生成混在一起 |

**与七步协议的关系：**方法设计主要在建立事实和设计检查中展开，对抗复查对应收敛与反驳，盲区历史对应报告与沉淀。五个 Skill 各有侧重，不表示每个 Skill 执行完整七步。

## 2. 规范：约束输出形式、具体程度和纠错义务

- **方法必须具体。** scan 要求贴合当前材料；用户指定重点时应围绕重点；必须包含“构造某种替代方案或情形，再诊断它”的动作。
- **发现必须可定位。** scan、reflect 与 full 的发现表要求位置、什么会出错、严重程度、可修复或结构性问题等字段。它们是定位和核查线索，不自动证明问题成立。
- **结论必须可以被反驳。** full 逐项追问什么证据可以推翻结论、是否过度断言、是否漏掉已有分析暗示的结果；错误要明确撤回。
- **范围必须交代。** scan 的结尾说明最大化了什么、未检查哪 1–2 个具体角度；reflect 用 MAXIMIZED / SACRIFICED / RECOMMENDATIONS 展开。
- **历史必须有结构。** reflect 追加时间、材料名、侧重点、遗漏与建议，供下次 scan 参考。

值得复用的是“每条问题可定位、每条结论可反驳、每次分析有范围说明”。如果增加证据引用、复现命令、置信度或验证状态，应明确这些是我们新增的规范。

## 3. 角度：约束从哪里看，以及采取什么检查动作

| 层次 | 上游如何选择 | 实际检查动作 |
| --- | --- | --- |
| 研究领域 | discover 列约 10–20 个真正不同的方向，由用户选择 | 区分错误处理、安全、接口、用户理解、运维成本等；避免把同义问题拆成多个领域 |
| 当前重点 | scan 根据材料、用户指定重点和既往遗漏生成方法 | 把“检查性能”写成构造高负载、追踪锁争用等具体动作 |
| 结构 WHERE | 3way 逐层检查结构与依赖 | 哪层暴露什么、隐藏什么、依赖什么；新旧设计在哪里衔接不良 |
| 时间 WHEN | 3way 推演 3–5 个变化周期；simulation 固定五类维护变化 | 新人接手、依赖升级、作者离开、使用增长等条件下，什么会坏、固化或丢失 |
| 目标冲突 WHY | 3way 选择三个期望性质，尝试论证它们的冲突并构造替代设计 | 检查优化一个目标会牺牲什么；需要独立验证其假设和推导 |
| 固定模板 | 七份模板提供错误传播、结构权衡、性能、接口行为、信息损失、假设反转、长期演化等视角 | 追踪错误链、比较承诺与行为、把假设反过来、推演维护变化 |

可迁移的设计是把宽泛领域变成“观察对象 + 检查动作 + 具体产出”：例如 **并发 → 构造线程交错 → 给出违规状态转换与复现步骤**。单独写“全面、深入、多角度”没有规定 AI 实际要做哪些检查。

## 4. 如何实现这些限制，强度如何

上游主要通过 Markdown 中的阶段标题、角色指令、明确数量、输出字段、示例，以及“必须执行、不得跳过”等语句施加约束；这属于提示词引导。仓库没有提供逐阶段状态机、输出 schema 验证器、独立隔离的多模型审查器或测试验收门槛来保证遵守。

`allowed-tools` 等前置信息也要由宿主解释，实际工具权限和执行情况需要在宿主中验证。仅靠多角色一致、报告完整或格式规范，都不能确定结论正确。

## 5. 复用时保留什么、调整什么

**保留：**公开方法、阶段职责、反例构造、强制复查、统一发现字段和盲区记录。

**调整：**上游有些指令预设存在“守恒律”或“三个性质不能共存”。我们建议允许结论为“尚未发现必然冲突”或“证据不足”，并要求列出成立条件与可推翻它的证据。这是本研究的改进建议，不是已验证的效果提升。

现行可复用指令见 [七步协议与九项报告](web/assets/problem-diagnosis-protocol.txt)；[早期最小分析协议](web/assets/analysis-protocol.txt)仅作历史材料保留。它是我们的归纳与调整，不是上游原文，也不是新安装的 Skill。
