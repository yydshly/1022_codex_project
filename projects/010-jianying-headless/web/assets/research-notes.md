# 复用引擎，重建控制层：剪映无界面调用研究

研究日期：2026-10-22

依据固定源码、作者公开记录和本地 Git 保全结果整理；没有在本机验证剪映原生运行。扩展方向属于我们的研究提案。

## 我们的理解主线

逆向适配 → 复用剪映引擎 → 重建我们的控制层 → 按层扩展与验证。把剪映已有能力变成程序和 AI 可以编排的工具。

- 入口与产品层：我们的界面、AI 任务或批处理接收素材、剪辑目标和参数；程序也可以直接调用核心库。
- Skill：yichen-jianying-edit 给宿主 AI 操作规则与辅助脚本，指导计划、调用、时间映射和验收。
- 核心库：jianying-headless 构建轨道、素材与字幕等工程数据，桥接本机剪映的编解码、工程恢复和导出服务。
- 剪映底层引擎：匹配版本的本机程序库与原生资源继续提供原生处理和导出能力；原生路径依赖剪映安装。
- REA：通过 AI 与反编译工具辅助分析内部接口、数据结构和调用顺序，支持核心库适配；剪辑执行无需经过 REA。
- 产出：核心库构建可编辑草稿，可交回剪映精修；在已适配版本上由原生引擎导出视频。

### 我们可以扩展的三层（提案）

- 产品与工作流：自有界面、任务服务、批量多版本。
- AI 编排：剪辑策略、字幕与删留规则、验收规范。
- 草稿构建与桥接：更多工程字段与功能、完整调用链、版本和平台适配；REA 可辅助研究。

核心价值：把已有编辑能力接入 AI 编排、批量生产与人工精修，复用原生处理能力。

图示为已适配的原生路线。接口复用仍依赖剪映；新增能力须逐项验证，完整功能覆盖与独立重建尚未实现。原项目 Windows FFmpeg 后端属于另一条路线。

## 核心理解

- 已适配的无界面流程复用本机安装的剪映引擎及内部工程服务。
- 我们可以用计划、脚本、AI 或自有界面重新组织控制层，自动草稿仍能交回剪映精修。
- 复用引擎与独立重建的目标、依赖和工作量不同；界面存在某功能不意味着已经找到了完整调用链。
- 逆向分析需要继续落实为数据结构、初始化、调用顺序、版本适配与输出验收。

## 六步实现链路

### 1. 剪辑计划

用户或 AI 明确素材、删留、时间位置、速度、字幕和音量。Skill 提供操作规则；口播辅助脚本把保留区间编译为新的时间映射。语义判断主要由宿主 AI 承担，脚本检查发音保护、时间边界和一致性。

- 输入：本地素材、明确参数；需要语义剪辑时，提供同源时间戳稿或另行转写。
- 输出：结构化剪辑计划；口播流程还会产生编译后的时间映射。
- 关键点：先判断保留什么，再计算它放在哪里。语音转写是独立依赖，不由这个 Skill 自动获得。
- 源码位置：`scripts/edit_plan.py → from-compiled`
- [对应来源](https://github.com/mcncarl/yichen-skills/blob/9bd78982aa75aa179258bc9009fe4dcf2f2973b9/yichen-jianying-edit/references/plan-format.md)

### 2. 构造工程

核心以采集的原生结构蓝图为基础，创建轨道、片段、素材和 ID 关联，填入源时间、目标时间、速度及字幕。素材与字体按内容身份复制到独立草稿目录。它构造的是可编辑工程结构。

- 输入：经过检查的计划、原生结构蓝图、视频 / 音频 / 字体文件。
- 输出：轨道与素材关联、时间线对象、资源副本、工程元数据。
- 关键点：移动片段往往对应工程数据变更。很多编辑操作需要维护多处关联，并非调用一个同名按钮函数。
- 源码位置：`engine/jy14_headless.py · timeline_for() / build()`
- [对应来源](https://github.com/mcncarl/jianying-headless/blob/27c2627bbd0fccc8484000f32e9d66a820f4b698/engine/jy14_headless.py#L275)

### 3. 原生编解码

C++ 桥接器声明并调用剪映提供的 EncryptUtils 接口，对草稿内容进行编解码。Python 包装器从内存交接数据并执行回环检查。底层编解码实现由本机安装的剪映程序库提供。

- 输入：时间线和工程元数据；匹配版本的本机剪映程序库。
- 输出：剪映可以读取的草稿内容文件、元数据及相关镜像文件。
- 关键点：项目提供调用适配与文件处理；原始编解码实现没有被独立重写。源码本身不包含官方引擎。
- 源码位置：`bridge/jy14_codec.cpp · lvve::EncryptUtils`
- [对应来源](https://github.com/mcncarl/jianying-headless/blob/27c2627bbd0fccc8484000f32e9d66a820f4b698/bridge/jy14_codec.cpp#L547)

### 4. 本地登记

build 先在独立目录生成结果。需要交给剪映界面继续编辑时，publish 在确认剪映关闭后，将已验证草稿放入本机草稿目录并更新首页索引。用户之后可以打开、修改、保存和检查；原生导出也可以独立使用冻结的 build。

- 输入：已通过结构检查的独立草稿；本机首页索引与匹配运行环境。
- 输出：可从剪映首页打开的项目，以及登记与回读记录。
- 关键点：首页登记是可选交接步骤，不是无界面原生导出的必要前置条件。publish 只表示本地项目列表登记。
- 源码位置：`engine/jy14_headless.py · publish() / verify_live()`
- [对应来源](https://github.com/mcncarl/jianying-headless/blob/27c2627bbd0fccc8484000f32e9d66a820f4b698/engine/jy14_headless.py#L668)

### 5. 引擎导出

Python 编译 C++ 辅助程序并连接 libvideoeditor.dylib，在独立进程中初始化服务与会话、恢复工程，再构造原生导出请求。内部函数位置和对象布局按精确版本固定，完成事件也要核对。

- 输入：已验证的工程快照、匹配的剪映程序库、可用资源与导出设置。
- 输出：原生引擎渲染的 MP4、引擎日志和导出状态。
- 关键点：找到函数只是开始；初始化、对象布局、依赖和调用顺序同样重要。更新版本后需要重新适配与验证。
- 源码位置：`native_export.py → native_export.cpp → ExportService`
- [对应来源](https://github.com/mcncarl/jianying-headless/blob/27c2627bbd0fccc8484000f32e9d66a820f4b698/engine/native_export.cpp#L90)

### 6. 结果验收

导出包装器检查编码、尺寸、帧率、帧数和完整解码，并核对输入和来源工程未被改变。可编辑草稿还需要保存重开检查；字幕、切口、特效与听感要回到实际画面和声音核对。

- 输入：草稿与导出文件、冻结的预期设置、资源哈希和实际播放结果。
- 输出：结构 / 文件检查结果、实际视听结论，以及仍未解决的差异。
- 关键点：自动检查和主观检查回答不同问题。encoded-and-decoded 只代表相应文件检查通过。
- 源码位置：`native_export.py · validate_probe() / full decode`
- [对应来源](https://github.com/mcncarl/jianying-headless/blob/27c2627bbd0fccc8484000f32e9d66a820f4b698/engine/native_export.py#L517)

## 四个项目的分工

### jianying-headless · 工程与执行层

生成 / 修改草稿，登记、校验及已适配版本的原生导出。

依赖：本机匹配的剪映及其资源；Windows 另有 FFmpeg 后端。

研究状态：完整仓库已备份；固定版本 27c2627。

### yichen-jianying-edit · AI 操作与计划层

指导需求整理、口播删留、时间映射、工具调用和质检。

依赖：宿主 AI、核心仓库；按任务需要另行提供转写。

研究状态：所在完整仓库已备份；固定版本 9bd7898。

### jy-draftc · Windows 原生适配

加载 videoeditor.dll，调用草稿处理与无界面导出入口。

依赖：Windows x64、精确适配的剪映构建与依赖。

研究状态：公开源码已核对；本轮未备份；固定版本 4f705a9。

### REA · 逆向研究工具层

把反汇编、伪代码、引用和调用追踪等分析工具接给 Agent。

依赖：宿主 AI、对应分析工具与目标文件；结论仍需验证。

研究状态：官方说明已核对；本轮未备份；固定版本 905cbaf。

## 八个扩展方向（我们的提案，尚未实现）

### 1. 统一剪辑操作协议 / 先做基础

让需求表达稳定，让不同入口说同一种语言。

- 场景：AI、命令行和未来界面复用同一份计划，减少字段与时间语义的歧义。
- 复用：已有计划格式、草稿构建器、资源校验与独立副本策略。
- 新增工作：定义动作和错误模型，声明各后端能力，固定时间单位、素材身份与版本字段。
- 验收：同一计划重复执行的结构一致；未知动作、时间越界和版本不匹配有明确拒绝结果。

### 2. 口播初剪与人工复核 / 先做基础

把语义取舍接到时间线，同时保留人的判断。

- 场景：教程、课程和产品口播：标记重复表达与口误，整理字幕和补充画面。
- 复用：Skill 的删留规则、发音保护、时间映射及音频检查思路。
- 新增工作：接入有时间戳的转写，把不确定删留集中展示；增加前后对照和确认后的版本记录。
- 验收：关键语义、数字和完整发音保留；字幕对齐；剪口试听与草稿保存重开通过。

### 3. 建立原生结果回归样本 / 先做基础

让版本升级后的判断有一套可复跑的参照。

- 场景：升级剪映或扩展效果后，核对旧能力是否仍然成立。
- 复用：快照、素材哈希、帧数检查、完整解码、冷重开回读与导出日志。
- 新增工作：准备可公开或可授权使用的小样本，覆盖静音片段、变速、字幕、叠加和尾帧；保存参考画面与音频。
- 验收：相同构建能复跑；画面差异、响度偏差、缺帧和工程持久化问题分别报告。

### 4. 素材替换与多版本生产 / 扩展工作流

复用已确认的结构，改变画面、文字和配音。

- 场景：同一讲解结构生成多个素材版本，或统一更新系列视频中的字幕与片段。
- 复用：已有草稿的独立副本编辑、replace_text、replace_media 和音量调整。
- 新增工作：设计可替换素材位置与约束，检查时长及裁切；组织并行任务、失败隔离和每版来源记录。
- 验收：原稿未变；新素材时长与引用有效；每版单独完成画面、声音和导出检查。

### 5. 封装本地工具服务 / MCP / 扩展工作流

让 AI 使用有边界、能检查结果的操作集合。

- 场景：Agent 按“检查 → 构建 → 复核 → 导出”的方式调度本机能力。
- 复用：现有命令入口、冻结快照、版本门禁与审计结果。
- 新增工作：定义工具参数、任务状态与取消机制；限制可操作目录；将长任务进度和错误变成结构化结果。
- 验收：重复请求不覆盖人工修改；异常可定位；只对已支持功能声明可用；结果能回查到具体工程。

### 6. 用 REA 辅助新增版本适配 / 继续研究

缩小未知范围，再用真实工程证明调用方法。

- 场景：剪映升级后查找内部函数、对象布局与初始化链路的变化。
- 复用：既有版本适配记录、桥接源码和回归样本；REA 的分析与引用追踪能力。
- 新增工作：比较目标二进制，记录函数候选与结构证据，独立验证调用顺序和资源依赖。
- 验收：通过精确构建指纹核对和真实原生用例；分析工具给出的猜测不能直接算兼容通过。

### 7. 面向特定任务的自有界面 / 继续研究

用更少的步骤，组织我们真正需要的剪辑能力。

- 场景：口播工作台、批量审片台或固定格式的内容生产界面。
- 复用：计划协议、草稿副本、引擎导出与已有剪映精修入口。
- 新增工作：实现任务界面、状态同步、撤销和修改记录；需要实时预览时，单独研究预览接入和性能。
- 验收：界面意图与工程结构一致；人工修改不被旧计划覆盖；每个开放操作都有完整验收路径。

### 8. 把控制层与渲染后端解耦 / 继续研究

为原生剪映、FFmpeg 和未来后端保留清晰边界。

- 场景：上层沿用同一计划，根据能力选择不同执行后端。
- 复用：原项目已有 Mac 原生与 Windows FFmpeg 两种路径，可作为边界样本。
- 新增工作：建立能力矩阵和语义映射；明确哪些效果可对应、哪些需要拒绝；独立后端的算法仍需另行实现。
- 验收：相同计划只在双方已定义的共同范围内比较；差异有记录，不把功能名相同当作输出完全一致。

## 两种工程目标

### 复用剪映引擎

保留剪映提供的工程服务与渲染能力，把精力放在调用适配、操作编排和实际任务体验上。

仍依赖匹配的剪映运行时、资源与相应使用条件。

- 研究数据结构、初始化和内部接口调用顺序。
- 实现计划协议、独立草稿、AI 工具或自有界面。
- 维护版本适配、错误处理与实际输出回归。

可以逐步扩大已验证的本地功能范围；没有依据预先保证界面中大部分或全部功能都能独立调用。

### 完全独立重建

脱离剪映运行时，使用自己的实现或其他后端处理时间线、画面、音频与效果。逆向分析为理解行为提供线索。

目标是不再依赖剪映程序库；需要自行建立相应后端、资源和服务。

- 把选定功能还原为明确行为与测试条件。
- 重写相应算法、工程模型、预览与导出后端。
- 核对复杂素材、长时间线、性能、稳定性与兼容性。

可以先重建有限功能。完整产品的一致性是另一层目标；客户端未包含的云端实现或数据，也不能只靠本机分析获得。

## 对话问题

### 它本质上是不是逆向找到接口，再直接调用？

方向正确。项目确实适配内部接口，但还需要构造正确的工程、对象和参数，完成初始化与状态等待，再验证结果。函数地址只是调用链的一部分。

### 是不是把剪映上层抛弃了？

更准确地说，替换的是用户操作入口和一部分编排方式。内部工程恢复、服务和渲染仍可能来自剪映。原界面也可以保留，继续精修可编辑草稿。

### 界面里能做的功能，理论上都能调用吗？

很多本地能力有进一步适配的空间，但不能直接推出全部可用。有的操作要重建上层逻辑、组合多项服务；有的还依赖资源、账号或在线服务。每项能力需要独立证明。

### Windows 为什么不能直接照搬 Mac 实现？

两个平台的程序库、编译环境、内部函数位置和对象布局需要分别适配。Windows 已有 jy-draftc 的原生路线；原项目 Windows 使用 FFmpeg，是它当前实现范围的选择。作者最初为何选择 Mac，本次没有找到明确说明。

### 有了 REA，是否就能完整复刻剪映？

REA 可以辅助定位函数、理解调用关系并支持实现验证。复用剪映引擎和独立重写剪映是两个目标；后者还要承担算法、后端、资源和产品兼容性，不能从局部分析成功推出完整复刻已可完成。

### 最实际的价值，落在哪里？

把 AI 产生的剪辑判断落实成可编辑时间线，让人能继续精修；把重复操作沉淀为计划、批处理和工具接口；同时复用已有渲染能力。实际效率提升与覆盖范围仍需用具体任务验证。
