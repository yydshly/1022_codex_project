# 核心理解 · 光照效果实现与可复用价值

这个库的核心，是在浏览器里实现三维场景的光照效果：让几何与材质按照光源、空间关系和数值近似产生明暗、反弹光、阴影及反射，并与水面、植被、大气和后期组成完整画面。最值得沉淀的是光照计算与渲染管线，以及与之协同的环境表现方法。

## 用一栋房子理解原理

太阳照在红墙上，墙会把偏红的光反射到附近白球与地面。只有直接光时，背光区域容易缺少层次；加入间接光后，周围物体的颜色和空间关系会影响画面。

| 步骤 | 实现方法 | 通俗理解 |
| --- | --- | --- |
| 定义场景 | 几何、材质、光源、相机与 SceneHost | 先知道物体在哪里、表面是什么、从哪里看 |
| 查找光路 | BVH 加速射线与几何求交 | 快速判断光线被谁挡住、碰到哪里 |
| 估计反弹光 | Surfel 表面采样、迭代与加权估计 | 测一批方向，估计周围给来的光 |
| 保存照明 | Lightmap 和三维空间探针 | 静态表面查照明贴图，其他接收对象从空间取光 |
| 持续成像 | 逐帧读取缓存，更新直接光与阴影，组合材质和环境，经过后期输出 | 用已有计算结果支撑连续交互与换视角 |

这是显式三维渲染。几何、材质和光源提供共同依据；常见 AI 单图重绘则按图片、提示与可选结构条件生成外观。本库没有现成 AI 接口，后续可以另外用 AI 辅助准备贴图、概念或资产。渲染也有采样、离散化和缓存误差，不能把画面可信等同于绝对物理准确。

**更新规则很关键**：仅换相机可直接重绘；移动太阳后，直接光与阴影会变化，静态间接光仍需检查缓存并重烘焙。现有指定配置不代表任意动态场景都获得全实时 GI。

## 能实现哪些肉眼可见的效果

| 效果 | 用户看见什么 | 本次证据与范围 |
| --- | --- | --- |
| 反弹光与环境补光 | 彩色墙面影响附近物体，暗处保留层次 | Cornell Box 主管线指定配置已运行 |
| 太阳照明与阴影 | 太阳角度改变，受光面与投影变化；强度改变明暗 | 四场景共用真实太阳控制，静态间接光另行重烘焙 |
| 建筑与自然环境的组合 | 房屋、码头、船、植被、海岸和水面处于共同三维空间 | 完整海岸村庄已运行 |
| 浅水与棕榈 | 水下景物、波纹、泡沫、浮球与植物对光线和视角的响应 | 海滩原浅水 Worker 与植被更新已运行；可选房车缺模型而关闭 |
| 针叶林与溪流 | 树群遮挡、地表层次与溪流波纹 | 森林已运行；溪流为不透明波纹材质，与海滩浅水系统不同 |
| 反射、天空、大气与镜头效果 | 表面环境响应、远景空气层次、曝光、颜色与抗锯齿 | 源码中有对应接入或实验；本次展示统一关闭部分反射、雾等通道，需按场景配置验证 |

四个场景可以切换，并调太阳方位、高度、强度与相机环绕、仰角、距离。完整实测配置、原始截图、补采样修复和告警见 [RUNTIME.md](RUNTIME.md)。89 项能力是源码研究条目，四场景通过不能代表全库画质、性能或跨设备验收。

## 可以沉淀和复用什么

| 可沉淀的部分 | 后续价值 | 集成时要做的工作 |
| --- | --- | --- |
| 光照准备与缓存 | 避免每帧重复求全部间接光 | 定义静态与动态范围、缓存来源与失效规则 |
| Lightmap / 探针接收路径 | 支持表面与空间位置相关的环境光 | 检查几何、UV、探针覆盖、密度与漏光 |
| 太阳与阴影控制 | 保持光源参数与画面变化有明确关系 | 接入目标项目的时间、灯光与重烘焙策略 |
| 水面、植被和自然材质 | 构建海岸、岛屿、森林等环境 | 按真实模块选择素材、模拟方式与成本 |
| 帧流程与画面合成 | 统一组织绘制、计算、缓冲与后期 | 梳理场景接口、渲染顺序与可选通道 |
| 诊断工具与证据方法 | 分开定位画质、缓存和性能问题 | 固定参数，拆通道，在目标设备上测量 |

它适合作为自己渲染底座的研究起点。当前仍需工程整理，不能直接当成已封装好的通用引擎插件。

## 可以用在哪些场景，怎样扩展

- **浏览器游戏**：海岛探索、农场、场景漫游等可以复用环境光、阴影、水面和植被。继续接入自有角色、相机、交互与资产；操作、任务、战斗、存档和联网等由游戏项目实现。
- **建筑与空间漫游**：展示室内外的受光关系、材质和空间层次。继续接入建筑模型、室内外照明区域和漫游交互；这里的光照可视化不等于定量建筑日照分析。
- **产品与 Web3D 展厅**：组织相机、光源、材质、阴影和环境响应。继续加入产品资产、热点与参数切换，对需要的反射路径单独调优。
- **图形学教学与研究**：比较直接光和间接光，观察缓存、采样、阴影、流体和后期的取舍。继续补接独立实验室、可重复的参数方案与目标设备基准。
- **时间、天气与动态内容**：可以沿现有太阳、大气和动态几何路径进一步开发；应先明确哪些通道实时更新、哪些缓存需重算，再评估成本，不能只移动太阳就声称整个世界照明已正确更新。

上述方向是基于已有能力的扩展推导，需要在目标项目逐项集成和验收。

## 复用时的准确边界

需要 WebGPU 及足够的计算上限，依赖作者 Three.js / React Three Fiber fork 的固定版本。本研究记录了一条有效表面补采样修复，并保留原正确性检查；细小画质告警与跨设备性能仍有验证空间。原始快照未提供仓库级 LICENSE，来源和依赖声明见 [NOTICE.md](NOTICE.md)。

建议的工程路线是：**固定版本 → 梳理场景接口 → 整理资产和缓存 → 选择必需效果 → 调整预算 → 在目标设备验收**。将这些环节连起来，才能把“看过一个好看的演示”变成“项目中可维护、可复用的渲染能力”。
